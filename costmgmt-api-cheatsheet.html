Introduction

The Cost Management API allows users to obtain all the data available in the UI, and even more since with the API it’s possible to combine filters or to make several API calls and then combine the results.

The latest version of this cheat sheet, and its accompanying Bruno collection, are always available from https://github.com/project-koku/costmgmt-api-cheatsheet.

Below are common scenarios with example API calls.

Base URL: https://console.redhat.com

Authentication

Using service account tokens (OAuth2 client credentials)

Grab your token using the following curl command:

curl -v \
  -d "client_id=CLIENT_ID" \
  -d "client_secret=CLIENT_SECRET" \
  -d "grant_type=client_credentials" \
  -d "scope=api.console" \
  "https://sso.redhat.com/auth/realms/redhat-external/protocol/openid-connect/token"

Use the token in an API request via curl:

curl --location \
  'https://console.redhat.com/api/cost-management/v1/reports/aws/costs/' \
  --header 'Authorization: Bearer ACCESS_TOKEN'

Fleet summary

Cross-cluster aggregated savings, adoption rates, and top optimization opportunities:

GET /api/cost-management/v1/recommendations/openshift/fleet-summary

Fleet savings summary

Aggregated monthly savings by plugin (container, node, PVC, snapshot, VM). Container, node, and VM totals honor ?engine=cost (default) or performance. GPU dollar estimates are computed at API read time and are excluded from this rollup (by_plugin.gpu is always 0; see gpu_savings_note).

Use ?term=short, ?term=medium (default), or ?term=long to align node/container/PVC rollups with the same term window as list APIs. VM savings use mapped term keys (short_term, medium_term, long_term).

Requires persisted recommendations for the selected term. VM rows need ROS_SAVINGS_ESTIMATES_ENABLED=true and KOKU_MASU_URL at ingestion time for non-zero by_plugin.vm.

GET /api/cost-management/v1/recommendations/openshift/savings-summary
GET /api/cost-management/v1/recommendations/openshift/savings-summary?engine=cost
GET /api/cost-management/v1/recommendations/openshift/savings-summary?engine=cost&term=short
GET /api/cost-management/v1/recommendations/openshift/savings-summary?filter[cluster]=<cluster-uuid>&group_by[tag:environment]=*
GET /api/cost-management/v1/recommendations/openshift/savings-summary?group_by[tag:environment]=*
Note
 filter[cluster] is only applied when a group_by parameter is present (e.g., group_by[tag:*] or group_by[idle_state]). Without group_by, the filter has no effect and all RBAC-visible clusters are included.

Savings recalculation (internal)

After a Koku cost model update, masu notifies ROS to refresh persisted dollar savings without re-ingestion. Supported types: container, node, pvc, quota, cluster-quota. Service-account bearer token required (same auth as tag sync). Requires ROS_SAVINGS_ESTIMATES_ENABLED and ROS_SAVINGS_RECALCULATION_ENABLED.

POST /api/cost-management/v1/internal/recalculate-savings

Example body:

{
  "org_id": "1234567",
  "cluster_uuid": "02059694-68ab-4d58-8809-de1e91f1d0e5",
  "recommendation_types": ["container", "node", "pvc", "quota", "cluster-quota"]
}

Returns 202 Accepted with status: "accepted"; work runs asynchronously.

Example response excerpt:

{
  "currency": "USD",
  "estimated_monthly_savings": { "value": "12500.750000", "units": "USD" },

    "pvc": 1500.0,
    "snapshot": 500.0,
    "vm": 1200.0,
    "gpu": 0.0
  },
  "gpu_savings_note": "GPU savings are computed at API read time..."
}

Container recommendations

All container-level CPU/memory right-sizing recommendations:

GET /api/cost-management/v1/recommendations/openshift/

Recommendations for a specific container (use the recommendation UUID):

GET /api/cost-management/v1/recommendations/openshift/{recommendation_uuid}

The detail response includes per-term (short/medium/long) recommendations for two models:

  • Cost model: optimizes for resource savings (p60 CPU / p95 memory)

  • Performance model: optimizes for headroom (p98 CPU / p100 memory)

Each recommendation includes CPU/memory requests and limits, notifications, and usage distribution box plots (min, Q1, median, Q3, max).

Detail responses nest both engines under each term:

recommendations.recommendation_terms.medium_term.recommendation_engines.cost
recommendations.recommendation_terms.medium_term.recommendation_engines.performance

How engines differ (cost vs performance)

  • Cost — lower usage percentiles (e.g. P60 CPU, P95 memory) to right-size for savings

  • Performance — higher percentiles (e.g. P98 CPU, max memory) to preserve headroom

On list endpoints, filter[engine]=cost or filter[engine]=performance returns only the selected engine under each term and omits the other from recommendation_engines. When the filter is omitted, both engines are returned.

To generate cluster data where cost and performance sizing intentionally diverge (for validation or demos), use the NISE fixture at nise/examples/ocp_dual_engine/ (spike-cpu-api, steady-mem-worker workloads; see the README in that directory).

Testing divergence

After ingesting nise/examples/ocp_dual_engine/ data, container cost vs performance sizing will differ under recommendation_terms.*.recommendation_engines (higher CPU/memory on performance for spike-prone workloads). Use that fixture in your test cluster to verify dual-engine divergence in E2E, IQE, or Bruno manual runs; generic fixtures may return identical sizing while still exposing both engine blocks.

Filtering and sorting

Filter by cluster, project, workload, workload type, or container:

GET /api/cost-management/v1/recommendations/openshift/?filter[cluster]=CLUSTER_UUID
GET /api/cost-management/v1/recommendations/openshift/?filter[project]=my-namespace
GET /api/cost-management/v1/recommendations/openshift/?filter[namespace]=my-namespace
GET /api/cost-management/v1/recommendations/openshift/?filter[workload]=my-deployment
GET /api/cost-management/v1/recommendations/openshift/?filter[workload_type]=deployment
GET /api/cost-management/v1/recommendations/openshift/?filter[container]=my-container

filter[namespace] is an alias for filter[project] (both filter by OpenShift namespace). Legacy flat forms (cluster_uuid, project, namespace, container) are also accepted.

filter[workload_type] accepts lowercase Kubernetes controller kinds (exact match; comma-separated values are ORed): daemonset, deployment, deploymentconfig, replicaset, replicationcontroller, statefulset. Legacy flat form ?workload_type=deployment is also accepted.

Filter by recommendation engine (limits nested recommendation_engines to cost or performance; omits the non-selected engine from each item):

GET /api/cost-management/v1/recommendations/openshift/?filter[engine]=cost
GET /api/cost-management/v1/recommendations/openshift/?filter[engine]=performance

Legacy flat ?engine=cost is also accepted on container, namespace, node, VM, quality, and history endpoints.

Filter by GPU:

GET /api/cost-management/v1/recommendations/openshift/?filter[has_gpu]=true
GET /api/cost-management/v1/recommendations/openshift/?filter[gpu_model]=A100
GET /api/cost-management/v1/recommendations/openshift/?filter[gpu_classification]=underutilized

Filter by idle state (active, idle, or zombie; comma-separated values are ORed):

Note
 The API uses idle_state=zombie which the UI displays as "Abandoned". 
GET /api/cost-management/v1/recommendations/openshift/?filter[idle_state]=zombie,idle

Filter by OpenShift labels (requires ROS_TAGS_ENABLED=true; tags synced from Koku):

GET /api/cost-management/v1/recommendations/openshift/?filter[tag:environment]=production
GET /api/cost-management/v1/recommendations/openshift/?filter[tag:environment]=production,staging
GET /api/cost-management/v1/recommendations/openshift/?filter[tag:team]=platform

Tag filter syntax follows Koku report conventions:

  • filter[tag:<key>]=<value> — exact value match

  • filter[tag:<key>]=a,b — OR within the same key (comma-separated)

  • Multiple filter[tag:*] keys — AND across keys

  • filter[tag:<key>]=* — key present with any value

  • Legacy flat form ?tag=<key>:<value> is also accepted

When a tag key is unknown or has no matching containers, meta.count is 0 and meta.warnings may describe the empty result.

Pagination

GET /api/cost-management/v1/recommendations/openshift/?limit=20&offset=0

Sorting

Allowed order_by values: cluster, project, workload_type, workload, container, last_reported, cpu_request_current, memory_request_current, and per-term variation fields: cpu_variation_short_cost, cpu_variation_short_performance, cpu_variation_medium_cost, cpu_variation_medium_performance, cpu_variation_long_cost, cpu_variation_long_performance, memory_variation_short_cost, memory_variation_short_performance, memory_variation_medium_cost, memory_variation_medium_performance, memory_variation_long_cost, memory_variation_long_performance.

GET /api/cost-management/v1/recommendations/openshift/?order_by=last_reported&order_how=desc
GET /api/cost-management/v1/recommendations/openshift/?order_by=cpu_variation_medium_cost&order_how=desc

CSV export

Export container recommendations as CSV (one row per container × term × engine):

GET /api/cost-management/v1/recommendations/openshift/?format=csv
GET /api/cost-management/v1/recommendations/openshift/?format=csv&limit=100&order_by=last_reported&order_how=desc

Prefer Accept: text/csv for explicit content negotiation. Response Content-Type is text/csv. The export is capped at 1000 list records (up to 6000 CSV rows when all three terms and both engines are present). Columns include cluster, project, workload, container, savings, idle state, and per-term CPU/memory requests and limits. Use the same filters and order_by parameters as the JSON list endpoint.

History and quality

Node recommendations do not expose a history or quality API. Per-node history is N/A; GET …​/quality applies to container recommendations only (stability, adoption, OOM after rec).

Recommendation snapshot history (fleet-wide, native engine — containers):

GET /api/cost-management/v1/recommendations/openshift/history?limit=10
GET /api/cost-management/v1/recommendations/openshift/history?container=my-container&filter[engine]=cost&term=medium

History accepts filter[engine]=cost|performance (preferred) or legacy flat ?engine=cost.

Recommendation quality metrics (stability, adoption, OOM after rec):

GET /api/cost-management/v1/recommendations/openshift/quality?limit=10
GET /api/cost-management/v1/recommendations/openshift/quality?filter[engine]=cost&limit=10
GET /api/cost-management/v1/recommendations/openshift/quality?order_by=stability&order_how=desc

Replica counts and total savings

Container detail responses include replica information collected from kube-state-metrics (deployments, statefulsets, daemonsets):

  • replica_info.desired — spec-level replica count

  • replica_info.available — currently available/ready replicas

  • replica_info.source — "kube_state_metrics" (authoritative) or "derived" (pod count fallback)

Total impact savings multiply per-container savings by replica count.

NVIDIA MIG (Multi-Instance GPU) recommendations

MIG bin-packing recommendations appear in the container detail response and in a dedicated list endpoint.

Detail response — when a container uses a MIG-capable GPU (A100, H100, H200, B200), the response includes a gpu object with:

  • current_gpu_model / current_gpu_profile — what the container currently uses

  • recommended_gpu_profile — smallest MIG profile whose resources cover p95 usage

  • gpu_classification — e.g. compute_bound, memory_bound, underutilized

  • estimated_monthly_gpu_savings_usd — dollar savings from MIG right-sizing

GET /api/cost-management/v1/recommendations/openshift/{recommendation_uuid}

GET /api/cost-management/v1/recommendations/openshift/gpu/mig

GET /api/cost-management/v1/recommendations/openshift/gpu/mig?order_by=estimated_monthly_gpu_savings_usd&order_how=desc

NVIDIA GPU time-slicing recommendations

Node-level GPU time-slicing consolidation guidance. Evaluates how many containers could share each physical GPU via nvidia.com/gpu.replicas:

GET /api/cost-management/v1/recommendations/openshift/gpu/timeslicing
GET /api/cost-management/v1/recommendations/openshift/gpu/timeslicing?limit=25&offset=0
GET /api/cost-management/v1/recommendations/openshift/gpu/timeslicing?node_name=my-gpu-node&gpu_model=T4

Returns per-node recommendations with:

  • gpu_model — NVIDIA GPU model on the node

  • recommended_replicas — suggested time-slicing replica count

  • savings_per_gpu_usd / total_node_savings_usd — estimated cost savings

Node CPU/memory utilization recommendations

Node-level right-sizing based on CPU and memory utilization patterns — identifies underutilized, overcommitted, stranded-resource, idle, and zombie nodes. One JSON object per node with nested recommendation_terms and dual engines (cost, performance).

Business hours are not applicable to node recommendations (they apply to container and namespace recommendations only).

GET /api/cost-management/v1/recommendations/openshift/nodes
GET /api/cost-management/v1/recommendations/openshift/nodes?limit=10&offset=0
GET /api/cost-management/v1/recommendations/openshift/nodes?filter[term]=medium&filter[engine]=cost
GET /api/cost-management/v1/recommendations/openshift/nodes?filter[cluster]=CLUSTER_UUID&filter[node]=worker-0&limit=1
GET /api/cost-management/v1/recommendations/openshift/nodes?format=csv

List filters (bracket syntax preferred): filter[cluster], filter[node], filter[term] (short|medium|long), filter[engine] (cost|performance), filter[is_underutilized], filter[is_overcommitted], filter[idle_state] (comma-separated active, idle, zombie), filter[stranded_resource] (cpu, memory, none), filter[instance_type], filter[machineset_name], filter[tag:<key>]=<value> (requires ROS_TAGS_ENABLED=true; nodes match when any workload namespace on the cluster has the label). Sort: order_by (estimated_monthly_savings default, or node), order_how (asc|desc). Pagination: limit, offset. Legacy flat params ?term=, ?engine=, ?cluster_uuid= still work.

RBAC: node list and detail require cost-management.openshift.node permission (node name scope) in addition to cluster access via cost-management.openshift.cluster. Empty results when the user has no intersecting cluster/node permissions.

Single-node detail: GET …​/nodes/{node}?filter[cluster]=CLUSTER_UUID (registered). List-filter equivalent: filter[node] + filter[cluster] with limit=1 (same response shape).

GET /api/cost-management/v1/recommendations/openshift/nodes?filter[is_underutilized]=true
GET /api/cost-management/v1/recommendations/openshift/nodes?filter[stranded_resource]=memory
GET /api/cost-management/v1/recommendations/openshift/nodes?filter[machineset_name]=worker

  • throughput_threshold_bps — sustained aggregate rx+tx P95 above this (bytes/sec; default 62500000 ≈ 500 Mbps)

  • pps_threshold — packets-per-second P95 threshold for alternate network-bound path (default 100000)

  • drop_ratio_bp — max daily drop ratio must exceed this in basis points (default 10 = 0.1%) with high PPS

  • sustained_days — days in the term window meeting throughput or PPS+drop criteria (default 7)

  • enable_network_series — when true, network-bound VMs may receive n1.* instance types (default true)

io — disk I/O profiling and pattern classification:

  • high_iops_threshold — total read+write p95 IOPS above this triggers code 39 (VM_HIGH_IO) (default 3000)

  • sequential_threshold_bytes — average I/O size (peak BPS / peak IOPS) ≥ this → io_profile.pattern sequential and code 58 (default 65536 = 64 KiB)

  • random_threshold_bytes — average I/O size < this → random and code 59 (default 16384 = 16 KiB); values between random and sequential thresholds yield mixed

  • min_iops_for_classification — peak IOPS below this → low-io (no pattern codes) (default 100)

gpu — VM GPU classification and vGPU time-slicing tunables:

  • idle_threshold_bp — SM utilization below this → idle classification (default 500 = 5%)

  • underutil_threshold_bp — below this but above idle → underutilized (default 3000 = 30%)

  • fb_saturation_mib — frame-buffer saturation threshold in MiB; 0 auto-detects from GPU catalog (default 0)

  • compute_saturation_threshold_bp — SM fraction at or above this → compute-saturated (default 8500 = 85%)

  • gpu_timeslice_min_replicas — minimum recommended_time_slice_count when time-slicing is advised (default 2)

  • gpu_timeslice_max_replicas — upper cap on slice count; reduced when DRAM exceeds penalty threshold (default 16)

  • gpu_timeslice_fb_safety_threshold_bp — do not recommend time-slicing when frame-buffer fraction ≥ this (default 8000 = 80%)

  • gpu_timeslice_dram_penalty_threshold_bp — when DRAM ≥ this, max replicas is halved (default 5000 = 50%)

Detail responses may include GPU fields gpu_timeslice_confidence (high, moderate, low, or empty), gpu_timeslice_rationale, and recommended_vgpu_profile when time-slicing or vGPU profile selection applies.

  • -10 or -30 with filter[time_scope_units]=day for the last 10 or 30 days.

  • -1, -2, or -3 with filter[time_scope_units]=month for the last 1, 2, or 3 months.

You can also use explicit start and end dates:

?start_date=2022-09-01&end_date=2022-09-10

Exclude filter

Exclude specific values from results. Works with the same dimensions as filter and group_by:

GET /api/cost-management/v1/reports/openshift/costs/?group_by[project]=*&exclude[project]=openshift-monitoring
GET /api/cost-management/v1/reports/aws/costs/?group_by[account]=*&exclude[account]=123456789012

Pagination

All list endpoints support limit and offset for pagination:

?limit=10&offset=0

The response meta object includes count (total items) and links includes first, next, previous, last URLs.

Get CSV or JSON Reports

Any of the report endpoints can return CSV format by setting the Accept header to text/csv.

Any of the report endpoints can return JSON format by setting the Accept header to application/json.

Current month aggregation by cluster:

curl --location -g \
  'https://console.redhat.com/api/cost-management/v1/reports/openshift/costs/?filter[time_scope_units]=month&filter[time_scope_value]=-1&filter[resolution]=monthly&group_by[cluster]=*' \
  -H 'accept: text/csv' \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -o output.csv

Current month aggregation by project:

curl --location -g \
  'https://console.redhat.com/api/cost-management/v1/reports/openshift/costs/?filter[time_scope_units]=month&filter[time_scope_value]=-1&filter[resolution]=monthly&group_by[project]=*' \
  -H 'accept: text/csv' \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -o output.csv

Current month grouped per tag:

curl --location -g \
  'https://console.redhat.com/api/cost-management/v1/reports/openshift/costs/?filter[time_scope_units]=month&filter[time_scope_value]=-1&filter[resolution]=monthly&group_by[tag:tag_key]=tag_value' \
  -H 'accept: text/csv' \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -o output.csv

Current month combined group_by with filter (projects grouped, filtered by cluster and node):

curl --location -g \
  'https://console.redhat.com/api/cost-management/v1/reports/openshift/costs/?filter[time_scope_units]=month&filter[time_scope_value]=-1&filter[resolution]=monthly&group_by[project]=*&filter[cluster]=my_cluster&filter[node]=my_node' \
  -H 'accept: text/csv' \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -o output.csv

All of the above examples and additional parameter/filter options can be used with CSV export.
